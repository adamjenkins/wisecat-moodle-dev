# Contributing to wisecat-moodle-dev

This repository is a Claude Code plugin: skills, slash commands and subagents for Moodle plugin and theme
development, plus generated adapters for other coding assistants.

## Project layout

```
.claude-plugin/                     plugin + marketplace manifests
skills/<name>/SKILL.md              the skill: what holds on every supported Moodle version
skills/<name>/reference/<topic>.md  detail that is read only when a stated condition applies
skills/<name>/versions/moodle-X.Y.md  what is specific to one Moodle version
commands/<name>.md                  /<name> slash commands
agents/<name>.md                    subagents
adapters/                           GENERATED by scripts/build-adapters.py; never edit by hand
docs/SUPPORTED_VERSIONS.md          which Moodle versions the skills cover, and how to add one
```

## The skill contract

Every skill follows these rules. They exist so that a model reads as little as it needs and can trust what it reads.

### 1. `SKILL.md`

```markdown
---
name: <kebab-name>
description: Use when <trigger>. Covers <topics>. Skip when <negative trigger>.
---

# <Title>

## Overview
One or two sentences.

## When to Use
- trigger scenarios
- **Skip when:** <negative trigger, naming the sibling skill to use instead>

## <Sections with the substance>

## Common mistakes
| Mistake | What happens | Fix |

## Reference files
| File | Read it when |

## Version notes
| Moodle | File |

## References
- https://moodledev.io/...
```

- `name` and `description` are each on **one line**, within the first five lines. The directory name equals `name`.
- The description starts with "Use when". It is what the model matches on: name concrete triggers (file names,
  function names, error messages), and say when to skip.
- **At most 400 lines.** CI fails a longer `SKILL.md`. Do not pad a short skill, and do not squeeze a long one by
  cutting the reasons: move detail into a reference file.
- `SKILL.md` holds what is needed on most uses of the skill: the mental model, the default recipe, the rules that
  prevent the common failures, and the tables that say where the rest is.
- No tab characters in any Markdown file.

### 2. Reference files: read only when needed

Detail that most tasks do not need goes in `skills/<name>/reference/<topic>.md`.

- `SKILL.md` lists every reference file in its **Reference files** table with a concrete condition in the
  "Read it when" column ("the theme supports right-to-left languages", "a setting must change the SCSS").
  "For more detail" is not a condition.
- A reference file starts with one line that repeats when to read it, and stands on its own: a reader who opens
  only that file and `SKILL.md` has everything.
- One hop only: a reference file does not send the reader to another reference file.
- Reference files have no line cap, but one file is one topic. Split by the question the reader is asking.
- Link with a relative Markdown link: `[reference/rtl.md](reference/rtl.md)`. The adapter generator copies the
  files and rewrites these links.

### 3. Version files: built to take a new Moodle version

The supported versions are listed in `docs/SUPPORTED_VERSIONS.md`. The lowest supported version is the **baseline**.

- The body of `SKILL.md` states what holds on **every** supported version.
- A difference that fits in one line stays inline, tagged in bold at the start of the line or sentence:
  `**5.3+:**`, `**5.2 only:**`.
- Anything longer (a table of moved symbols, a recipe that differs, a list of files that exist on one version)
  goes in `skills/<name>/versions/moodle-X.Y.md`. That file says only what is specific to X.Y against the
  baseline. `SKILL.md` lists the files in its **Version notes** table.
- A skill with no version-specific content has no `versions/` directory and no Version notes table.
- Never write "the latest Moodle" or "recent versions". Name the version.
- Adding Moodle X.Y to the repository is: a line in `docs/SUPPORTED_VERSIONS.md`, a `versions/moodle-X.Y.md` in
  each skill where something differs, and a `moodle-X-Y-changes` skill for the upgrade itself. Nothing in an
  existing `SKILL.md` body should need rewriting unless a rule stopped being true on every version.
- Dropping a version is the reverse: fold what is now universal into the bodies and delete its files.

### 4. How a rule is written

A rule a model will follow has four parts. Keep all four, in few words:

1. **The fact**, stated plainly ("a child theme does not inherit `rendererfactory`").
2. **The symptom** when it is ignored, as the developer sees it ("renderer overrides are silently not used").
3. **The fix**, as code or a command that can be copied.
4. **Where it comes from**: a core path relative to the Moodle root, with the version it was read or run on
   (`public/lib/classes/output/theme_config.php`, 5.3.0), or a moodledev.io URL.

- Show real Moodle code, never pseudo-code. A sample that is copied must run.
- Say how sure the claim is when it matters: "run on 5.3.0", "read in the 5.2 source, not run". Do not present a
  prediction as an observation.
- Write in plain sentences. No capital-letter emphasis, no "CRITICAL" or "you MUST": state the reason instead.
- Prefer moodledev.io over the old wiki. Where the official page is out of date, say so and cite the source file.
- One home for each rule. Another skill that needs it gives one line and names the skill that owns it.

### 5. Nothing private

Skills teach Moodle, not one team's setup. A rule never says where, when or to whom something happened. Leave out:
machine paths and host names, private tooling, the names of plugins a lesson came from, review reports, people's
names and anyone's words. Say "a filter plugin", "a Plugins directory reviewer". Name upstream tools
(`moodle-plugin-ci`, `phpcs`, `grunt`) and paths relative to the Moodle root.

## Add a slash command

Create `commands/<kebab-name>.md`:

```markdown
---
name: <kebab-name>
description: One line shown in /help
argument-hint: "[optional args]"
---

Instructions to the model. Use $ARGUMENTS for the user's input.
```

## Add a subagent

Create `agents/<kebab-name>.md`:

```markdown
---
name: <kebab-name>
description: When to invoke this agent.
tools: Read, Grep, Glob, Bash
---

System prompt for the agent.
```

## Before you commit

```
python3 scripts/build-adapters.py
tests/run.sh
```

- [ ] File and directory names are kebab-case; front matter `name` matches
- [ ] Every reference and version file is listed in its skill's tables, with a real condition
- [ ] Code samples are valid Moodle
- [ ] `CHANGELOG.md` updated under `## [Unreleased]`
- [ ] `adapters/` regenerated and committed, including new files
- [ ] The skill, command and agent counts in `README.md` and the manifests are right

## Versioning

Semver, in three places: `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` (`plugins[].version`) and
`CHANGELOG.md`.

- **patch**: a correction or a link fix
- **minor**: a new skill, command, agent or Moodle version
- **major**: a rename or removal

## Testing with Claude Code

```
/plugin marketplace add /absolute/path/to/wisecat-moodle-dev
/plugin install wisecat-moodle-dev@wisecat-moodle-dev
```

Then give Claude a Moodle task and confirm the right skill activates.
