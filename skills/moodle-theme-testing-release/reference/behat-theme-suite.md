# Behat for a theme: suites, contexts, overrides and the markup core steps need

Read this when writing a theme's Behat features or step definitions, overriding or blacklisting a core or Boost
context, running core features under the theme, or when a theme feature runs zero scenarios.

Evidence: `public/lib/behat/classes/behat_config_util.php`, `public/lib/behat/classes/util.php`,
`public/lib/tests/behat/behat_hooks.php` and `public/admin/tool/behat/cli/*.php` were read in 5.2 and 5.3.0; the
suite code is identical in both. A theme suite generated by `init.php` and three scenarios passing in it were run on
5.3.0. Everything else here was read in the source, not run.

## How suites are built

`behat_config_util::get_behat_suites()` builds one suite per theme:

1. It lists installed themes and keeps those whose `config.php` loads, whose `$THEME->name` equals the directory
   name, and whose `$THEME->hidefromselector` is false. A theme that fails any of these has no suite.
2. Each theme's own features are the `*.feature` files under `theme/<name>/tests/behat/` and its subdirectories.
   They are removed from the core feature list, so they never run in `default`.
3. The default theme (`theme_config::DEFAULT_THEME`, Boost) gets core features plus its own, and its suite is named
   `default`. Any other theme gets only its own features, unless it is named by `--add-core-features-to-theme`.
4. Features and tags listed in the theme's `blacklist.json` are removed; `@app` features are always removed from a
   non-default theme's suite.
5. A suite is created even when it has no features; running it reports no scenarios and succeeds.

Before every scenario of a non-default suite, `behat_hooks` calls `set_config('theme', <suite name>)`, and it loads
the theme's selector overrides when the suite changes. That is the whole mechanism by which a feature "runs under"
a theme.

## Commands

From the Moodle root, the directory that holds `public/`. On 5.2 and 5.3 the root `admin/cli/` has shims for the
general scripts only; the Behat and PHPUnit tools are reached through `public/admin/tool/`.

```bash
# Initialise once, with the options CI uses. Options are stored for the run.
php public/admin/tool/behat/cli/init.php --scss-deprecations

# The theme's own features.
php public/admin/tool/behat/cli/run.php --suite=mytheme --tags=@theme_mytheme

# One feature file.
php public/admin/tool/behat/cli/run.php --suite=mytheme public/theme/mytheme/tests/behat/mytheme.feature

# Core features under the theme: initialise with -a for this theme, then run a core tag in its suite.
php public/admin/tool/behat/cli/init.php --add-core-features-to-theme=mytheme --scss-deprecations
php public/admin/tool/behat/cli/run.php --suite=mytheme --tags=@core_course
```

- `-a` / `--add-core-features-to-theme` without a value, or with `ALL`, adds core features to every theme's suite; that multiplies the run time.
- The moodledev "running Behat" page implies a theme needs `-a` before its features can run. The code shows `-a` is
  needed only to run core features under the theme; its own features are always in its suite.
- Run options (`--scss-deprecations`, `--no-axe`, `--no-icon-deprecations`, **5.3+:** `--colourmode`) belong to
  `init.php`, `util.php --enable` and `util_single_run.php --enable`. The header Behat prints at the start of a run
  lists them under "Run optional tests"; read it.
- moodle-plugin-ci reruns failed scenarios twice by default (`--auto-rerun=2`). A scenario that passes only on a
  rerun is flaky, and the green job hides it. Run locally without reruns before trusting a new scenario.

## Theme CSS on the Behat site

- `util.php --enable` and `util_single_run.php --enable` call `behat_util::build_themes()`: every installed theme is
  compiled left-to-right with the settings it has at that moment, and the CSS is saved in the Behat data root.
- `behat_hooks` puts that saved CSS back into the theme cache before each JavaScript scenario
  (`behat_util::restore_saved_themes()`).
- So an SCSS edit needs a new `--enable` or `init.php`; a setting set by `set_config()` inside a scenario does not
  change the CSS until something resets the theme caches; and an RTL page is compiled on first request, not
  prebuilt.
- A compile failure during the build stores the parents' fallback CSS, so every themed scenario then runs against
  plain Boost. The compile test in PHPUnit is the place to catch that; Behat will not report it.

A step that resets the caches after a setting changed, for a theme's own context file:

```php
    /**
     * Resets the theme caches, so that settings saved with set_config() reach the compiled CSS.
     *
     * @Given the theme caches are reset
     */
    public function the_theme_caches_are_reset(): void {
        theme_reset_all_caches();
    }
```

Without it, saving the setting through the settings page in the scenario does the same, because a theme setting
that feeds the SCSS has `set_updatedcallback('theme_reset_all_caches')` (`moodle-theme-settings`).

In theme designer mode the stylesheet is served with a lifetime of `THEME_DESIGNER_CACHE_LIFETIME` seconds (10 by
default, `public/lib/csslib.php`), so a scenario that changes the SCSS and asserts within that time can see the old
CSS. A large Boost-based theme defines `define('THEME_DESIGNER_CACHE_LIFETIME', 0);` in the CI site's `config.php`
for its designer-mode scenarios. With moodle-plugin-ci, add it after the install step with
`moodle-plugin-ci add-config "define('THEME_DESIGNER_CACHE_LIFETIME', 0);"` (the command exists in 4.5.11; not run
here).

## Step definitions in a theme

Rules from `get_tests_for_theme()` and `get_behat_contexts_for_theme()`:

- Every file matching `behat_*.php` in `tests/behat/` or its subdirectories becomes a context of the theme's suite,
  keyed by its file name. The class inside must have exactly that name, or it is skipped as "poorly named".
- Theme contexts are not global. A step defined by the theme exists only in its suite, so only the theme's features
  can use it. (Contexts of other plugin types are global.)
- The context list starts from the theme's nearest parent's list (for a Boost child: core's contexts with Boost's
  overrides already applied), minus contexts named in `blacklist.json`, plus the theme's own.
- After merging, any context whose class is a parent class of another context in the list is removed. A theme class
  that extends `behat_navigation` therefore replaces `behat_navigation` in its suite.

### A theme's own steps

```php
<?php
// (GPL header)

/**
 * Step definitions for theme_mytheme.
 *
 * @package    theme_mytheme
 * @category   test
 * @copyright  2026 Your Name <you@example.com>
 * @license    http://www.gnu.org/copyleft/gpl.html GNU GPL v3 or later
 */

// No MOODLE_INTERNAL check: Behat can load this file before config.php.
require_once(__DIR__ . '/../../../../lib/behat/behat_base.php');

/**
 * Step definitions for theme_mytheme.
 *
 * @package    theme_mytheme
 * @copyright  2026 Your Name <you@example.com>
 * @license    http://www.gnu.org/copyleft/gpl.html GNU GPL v3 or later
 */
class behat_theme_mytheme extends behat_base {
    // The theme's steps go here.
}
```

Saved as `public/theme/mytheme/tests/behat/behat_theme_mytheme.php`. `__DIR__ . '/../../../../lib'` resolves to
`public/lib` on 5.2 and 5.3.

### Overriding a core or Boost step

Documented naming: `behat_theme_<theme>_behat_<corecontext>.php`. For a Boost child, extend Boost's override when one
exists, so Boost's fixes stay in force:

```php
<?php
// (GPL header)

/**
 * Navigation step overrides for theme_mytheme.
 *
 * @package    theme_mytheme
 * @category   test
 * @copyright  2026 Your Name <you@example.com>
 * @license    http://www.gnu.org/copyleft/gpl.html GNU GPL v3 or later
 */

// No MOODLE_INTERNAL check: Behat can load this file before config.php.
require_once(__DIR__ . '/../../../../lib/tests/behat/behat_navigation.php');
require_once(__DIR__ . '/../../../boost/tests/behat/behat_theme_boost_behat_navigation.php');

/**
 * Navigation step overrides for theme_mytheme.
 *
 * @package    theme_mytheme
 * @copyright  2026 Your Name <you@example.com>
 * @license    http://www.gnu.org/copyleft/gpl.html GNU GPL v3 or later
 */
class behat_theme_mytheme_behat_navigation extends behat_theme_boost_behat_navigation {
}
```

- An empty subclass is a valid file: it gives the suite a named place for later overrides and changes nothing now.
  A large Boost-based theme ships several of these.
- To change one step, redefine its method with the same step text. Boost marks such methods with an `@override`
  annotation followed by the step text (`public/theme/boost/tests/behat/behat_theme_boost_behat_navigation.php`).
- Boost's navigation override exists in 5.2 and 5.3. A child whose navigation markup differs from Boost's either
  overrides the affected steps again or removes Boost's context and lets core's apply.

### Selector overrides

To change what a named selector such as `"Save" "button"` matches under the theme, add
`tests/behat/behat_theme_mytheme_behat_named_partial_selectors.php` (class of the same name) or
`..._named_exact_selectors.php`. `behat_hooks` loads them when the suite starts
(`behat_config_util::get_behat_theme_selector_override_classname()`). Rarely needed for a Boost child.

## blacklist.json

`tests/behat/blacklist.json` in the theme, read by `get_blacklisted_tests_for_theme()`:

```json
{
    "contexts": [
        "behat_theme_boost_behat_navigation"
    ],
    "features": [
        "course/tests/behat/paged_course_navigation.feature"
    ],
    "tags": [
        "@core_reportbuilder"
    ]
}
```

- Feature paths are relative to the directory that holds `config.php`'s `$CFG->dirroot` (the `public/` directory
  on 5.2 and 5.3), so they start `lib/`, `course/`, `mod/`, not `public/`. A listed feature that does not exist
  stops initialisation with "Blacklisted feature ... not found" (checked against every feature of the site).
- A file that exists but decodes to nothing (empty, `{}`, invalid JSON) stops initialisation with
  "blacklist.json is empty". Do not commit a placeholder.
- It matters only for core features run under the theme with `-a`, and for contexts. Boost's own file removes
  seven core features that assume Boost-only behaviour (`public/theme/boost/tests/behat/blacklist.json`).

## Markup core steps depend on

A theme that rewrites layouts or headers must keep what core steps look for, or core features fail under it
(and so do the theme's own features that use those steps). Read in 5.3.0 step definitions and layout templates:

| Kept from | Ids and classes |
|---|---|
| Boost's layout template (`public/theme/boost/templates/drawers.mustache`) | `#page-wrapper`, `#page`, `#page-content`, `#region-main-box`, `#region-main`, `#topofscroll`, `#region-main-settings-menu` |
| Core header and footer templates (`public/lib/templates/full_header.mustache`) | `header#page-header`, `#page-navbar`, `#page-footer` |
| Navigation steps (`public/lib/tests/behat/behat_navigation.php`) | `.usermenu` with a `.dropdown-toggle` and `.dropdown-menu`; `.primary-navigation .navigation.primarynav-navbar`; `.secondary-navigation .navigation.secondarynav-tabbar`; `ul.more-nav`, `[data-region="moredropdown"]`, `li.dropdownmoremenu`; `nav[aria-label]` breadcrumb with `ol > li`; drawer toggles with `data-action` containing `toggle-drawer` or `closedrawer` |
| Block steps (`public/blocks/tests/behat/behat_blocks.php`) | `#region-main`, `[data-region="add-block-button"]` |
| The `"X" "region"` selector (`public/lib/behat/classes/partial_named_selector.php`) | a `div`, `section`, `aside`, `header` or `footer` whose id is X; core features use `region-main`, `sticky-footer`, `courseindex-content`, `page-header`, `page-content`, `page-footer` most |

Also from the Boost DOM: the block drawer sits outside `#page`, so a step scoped to `#page` does not find blocks.

## Generators and site state

- A theme that stores its own records can ship a Behat generator, `tests/generator/behat_theme_mytheme_generator.php`
  extending `behat_generator_base`, so features write `Given the following "theme_mytheme > banner" exists:`
  instead of clicking through settings. The general generator recipe is in `moodle-behat-testing`.
- `$CFG->enablemyhome` is 0 on new 5.2 and 5.3 sites: `/` redirects logged-out users to the login page and logged-in
  users to the dashboard, so a feature about the site home page starts with
  `Given the following config values are set as admin:` and `| enablemyhome | 1 |`
  (`public/admin/settings/appearance.php`, `public/index.php`; core features do the same).
- Shipped user tours are disabled on Behat sites (`public/admin/tool/usertours/classes/manager.php`), so they never
  block a scenario. On a normal site they do block scripted browser checks: a new user's first dashboard visit
  opens a tour that covers the page.
- `I set the field "X"` does not match an `aria-label`: Mink matches id, name, `<label>` text and placeholder. A
  form control that has only an `aria-label` needs an id and a `<label class="visually-hidden" for>`.
- Window sizes: `I change the viewport size to "mobile"` (also `tablet`, `small`, `medium`, `large` or `WxH`),
  defined in `public/lib/tests/behat/behat_general.php`.
